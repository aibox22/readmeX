# 按读者决策选择 README 骨架

骨架是顺序起点，不是必须填满的栏目。许可证用名称和链接，不展开全文；贡献流程、更新日志、安全报告和支持政策优先链接已有独立文档。不加作者署名。

## 库或 SDK：是否加入这个依赖？

1. 项目名、一句话说明和最多四枚可核验徽章。
2. 两到四句说明问题、方式和 API 形状。
3. 与已知替代方案的具体差异。
4. 最小完整用例与输出。
5. 安装、运行时/版本要求和验证命令。
6. 少数核心入口，完整 API 链接出去。
7. 实际状态与稳定性边界。
8. 文档、更多示例和许可证链接。

用例在安装之前：读者先判断 API 是否适合，再决定是否安装。

## CLI：是否替代已经安装的工具？

1. 项目名、一句话说明、一条真实命令及真实输出。
2. 与现有工具的具体差异。
3. 各支持平台的安装命令与前提。
4. 三到四条常用命令，文字解释用途。
5. 常用配置，其余链接出去。
6. 状态、版本/升级边界和许可证链接。

录屏或动画只补充效果，命令和输出仍写在 Markdown 中。

## 应用、服务或自托管产品：运行成本是否合适？

1. 项目名、一句话说明、带 alt 的截图。
2. 功能、受众和与托管/现有方案的差异。
3. 可验证的试用、容器启动或沙盒步骤。
4. 运行时、资源、外部服务和首次配置要求。
5. 安装与首个成功结果。
6. 架构短文或一张图加文字。
7. 已有的安全/数据处理事实，详文链接出去。
8. 状态、发布/升级边界、支持渠道和许可证。

## 框架或平台：是否值得长期建立在它之上？

1. 项目名和一句话说明。
2. 两到三个核心概念构成的心智模型。
3. 与替代方案的差异，以及明确不覆盖的场景。
4. 端到端的小应用示例。
5. 安装和脚手架命令。
6. 扩展点和已有生态。
7. 有证据的稳定性与支持边界，不新增长期承诺。
8. 文档、已有治理材料和许可证链接。

## 模板、启动器或学习资源：复制后会得到什么？

1. 项目名、一句话说明及使用后的结果。
2. 版本前提与假定知识。
3. 复制/脚手架命令和第一个实际步骤。
4. 简短目录说明。
5. 首先要改的内容。
6. 对应版本、实际验证时间或已知时效边界。
7. 许可证链接及必须保留的归属条款。

## 最小四节

单一用途的小项目四节足够：

1. 项目名和一句话说明。
2. 最小用例与输出或效果。
3. 安装/首个实际使用步骤。
4. 许可证名称与链接。

把必要的差异和状态融入前两节，不为凑章节添加架构、路线图或社区内容。限制性许可证是早期判断条件时，把其链接移到开头。
