# 审查流水线

入口已经完成扫描和一次性提问。本流水线读取 `<target>/.readmex/scan.json`、已有 README 和入口收集的答案，不再追加问题。只读仓库不能判断的新事实，降低主张或删除，并写入记分卡。

## 诊断

1. 通读实际显示的 README，记下首次阅读的困惑。检查 `.github/README.md` 等遮蔽副本；最终 README 仍放仓库根目录。
2. 从扫描定位清单、许可证、入口、示例、测试和发布配置，再读取源码。扫描是索引，不能代替逐项证据。
3. 运行机械检查，保存原始结果：

   ```bash
   python3 <skill>/scripts/readme_factor_audit.py <target> --output <target>/.readmex/review/audit.txt
   ```

   它报告标题、命令位置、图片、链接等事实，不执行用例、不判断主张，也不自动给分。
4. 按 [review-evidence.md](../references/review-evidence.md) 在干净环境执行安装和第一个用例，逐条把 README 主张对回源码；保存命令、输出、证据位置和未验证项。
5. 按 [review-scorecard.md](../references/review-scorecard.md) 写 `<target>/.readmex/review/scorecard.md`。开头声明个人采用、公司采购或两者；五项阻断逐项给证据，八项共 16 分，通过线为 14。修复只按单位时间回报排序。

**单独审查在此交出记分卡，并等待用户同意后才改写 README。** 这次诊断确认是唯一的中途交互例外，不是追加事实问卷。合并执行已经授权创建、审查和优化，写出记分卡后直接继续。

## 改写

按 [readme-skeletons.md](../references/readme-skeletons.md) 选符合读者决策的骨架，小项目用最小四节。先在内部比较三种一句话定位：机械功能、消除的问题、可以替代的东西；选择证据最充分的一句，不再次让用户选文案。

- 按身份、差异、用法、安装、细节、背景的漏斗顺序组织；限制性许可证靠前，以便读者尽早判断适用性。
- 写出具体差异、已知边界和诚实状态。没有证据的速度、规模、兼容性或“生产可用”主张降级或删除。
- 保留可核验、能回答采用问题的徽章，默认最多四枚。口号、意愿声明和无法核验的徽章删除。
- 关键事实、命令和输出写在 Markdown 中；图片提供 alt。长参考、教程和社区流程放在已有文档里，以短链接指向它们；不把贡献流程和更新日志展开到正文。
- 不加入作者署名，不写手工目录。单仓库只保留一个实际显示的 README；多包仓库根 README 负责路由到包级文档。
- 只在公司或采购受众下写一段企业信号，按已有证据说明支持预期、发布节奏、安全政策等；不创造响应时间、客户背书或治理承诺。
- 统一仓库 description、website、topics 和 social preview 与 README 的定位。在已有授权和可用工具范围内落实；缺权限或能力时，把可直接采用的描述、topics 和预览建议写入记分卡，不假称已经发布。

## 验收

重新运行机械检查、需要修复的安装/首例路径和记分卡。五项阻断全部 PASS 且八项至少 14/16 才可声明通过；无法执行或查证的项目保留 FAIL（未验证），列明限制。

最后用没有仓库上下文的新读者或新 agent 做记分卡中的冷读者五问；修复错误答案对应的问题。保存最终分数、被删或降级的主张、执行证据和未完成项。合并执行将最终 README 和记分卡交给优化流水线。
